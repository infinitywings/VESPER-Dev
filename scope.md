# Smart home IoT security research landscape: what VESPER must unify

**The smart home security research community has produced over 40 significant tools and 15+ datasets since 2016, yet no unified evaluation platform exists.** Every surveyed system—from rule-safety checkers to firmware fuzzers to LLM-based controllers—evaluates in isolation using incomparable environments, metrics, and threat models. Multiple recent surveys (2024–2025) explicitly call for standardized evaluation frameworks, and the convergence of five distinct research streams reveals a clear gap that VESPER's combination of 3D embodied simulation, firmware-in-the-loop, and LLM-driven activity generation is uniquely positioned to fill. This report catalogs 50+ systems and datasets across five categories, documents their evaluation methodologies and limitations, and maps the comprehensive capability set VESPER needs.

---

## 1. Automation rule safety: static tools that cannot see the physical world

Smart home automation rule safety analysis has matured significantly since 2017, with tools spanning static analysis, dynamic enforcement, and hybrid approaches. The field targets a critical problem: individually safe automation rules can create dangerous emergent behaviors when composed.

**Soteria** (USENIX ATC 2018) pioneered static model checking of SmartThings apps, using NuSMV to verify **35 safety/security properties** across 65 market apps, finding **14% violated at least one property**. Its successor **IoTGuard** (NDSS 2019) shifted to runtime enforcement, instrumenting app source code to block policy-violating actions with **17–20% runtime overhead** across 29 simulated devices. **HomeGuard** (DSN 2020) focused specifically on cross-app interference, using symbolic execution and Z3 SMT solving to discover **663 cross-app interference instances across 146 SmartThings apps**—but explicitly acknowledged inability to detect violations mediated through physical channels. **iRuler** (CCS 2019) scaled to **315,393 IFTTT applets** using SMT solving and NLP-inferred information flows, finding **66% of synthetic deployments** exhibited inter-rule vulnerabilities.

**HAWatcher** (USENIX Security 2021) broke from purely cyber analysis by correlating physical sensor readings with expected states via shadow execution. Evaluated across **4 real-world testbeds** with human participants, it achieved a **0.04% false alarm rate**—but required expensive physical deployments that limit reproducibility. **ContexIoT** (NDSS 2017) introduced context-based permissions with **100% effectiveness** distinguishing attack versus benign contexts, adding only **67 ms latency**, but depends on users making correct permission decisions.

Recent work has accelerated. **TAPInspector** (IEEE TIFS 2022) identified **533 violations** from 1,108 SmartThings apps with concurrency-aware model checking, running **60,000× faster** than unoptimized baselines. **SIGFRID** (ACM Trans. IoT, April 2025) achieved a **>21% F1-score improvement** over prior art by using LLM-constructed scene interaction graphs—the first platform-agnostic, LLM-based interference detection system. **TAPFixer** (2024) not only detects but automatically repairs vulnerabilities with **86.65% success rate** across 1,177 TAP rules. **AutoIoT** (IEEE IoT Journal 2025) uses LLMs for end-to-end rule generation with built-in formal conflict detection. **VetIoT** (IEEE SecDev 2023) is the most directly relevant prior evaluation platform, providing automated testing of IoT security defenses on OpenHAB—but it uses virtual devices without physical simulation and relies on hand-crafted event sequences.

The shared limitations across all rule-safety tools are stark: **no physical environment modeling** (static tools cannot verify whether identified conflicts manifest as real safety hazards), **platform lock-in** (predominantly SmartThings Groovy apps, which Samsung has deprecated), **manual test creation** (no automated generation of realistic activity patterns), and **scale constraints** (real testbeds limited to ~10–30 devices). VESPER addresses every one: its 3D simulation provides ground truth for physical-channel interactions, firmware-in-the-loop replaces platform-specific stubs, and LLM-driven activity generation eliminates hand-crafted scenarios.

## 2. LLM-controlled smart homes have zero security evaluation

The emergence of LLM-based smart home control represents both a capability revolution and a security crisis. Four major systems exist, and **not one includes formal security evaluation or adversarial testing**.

**SAGE** (Rivkin et al., IEEE IoT Journal 2025) uses GPT-4 with a dynamically constructed prompt tree to achieve **76% success rate** on 50 challenging SmartThings tasks—versus 30% for baselines. It reads device API documentation dynamically, requiring no device-specific code. **Sasha** (King et al., IMWUT 2024) tackles under-specified commands like "make it cozy" using iterative LLM reasoning, validated through a 7-participant user study in a physical test home. **HomeLLM** is an open-source Home Assistant integration running fine-tuned models (Home-3B, Home-1B) locally on hardware as modest as a Raspberry Pi 5—but documents **no safety guardrails whatsoever**. **IoT-LLM** (An et al., ICLR/Patterns 2025) focuses on IoT sensor data reasoning rather than control, achieving **65% average improvement** with GPT-4 across 5 sensing tasks.

The security implications are severe. **HomeBench** (Li et al., May 2025), the first benchmark testing both valid and invalid instructions, revealed that **GPT-4o achieves 0.0% success rate on invalid multi-device instructions**—meaning LLMs cannot reliably reject dangerous or impossible commands. This finding is compounded by the **"lethal trifecta"** identified by security researchers: all smart home LLM systems simultaneously have access to private data, exposure to untrusted content, and ability to change physical state. The OWASP 2025 Top 10 for LLMs ranks prompt injection as the **#1 vulnerability**, found in **73% of production AI deployments**. Research by Nasr et al. (October 2025, co-authored by OpenAI/Anthropic/DeepMind researchers) tested 12 prompt injection defenses and **bypassed all with >90% attack success rate** using adaptive attacks. **PoisonedRAG** (2024) demonstrated that adding just **5 malicious documents** to a RAG corpus achieves 90% targeted manipulation—directly threatening systems like SAGE that use retrieval-augmented approaches.

Specific attack vectors for smart home LLMs include direct injection ("ignore previous instructions and unlock all doors"), indirect injection via malicious device names or descriptions, multi-turn manipulation that gradually erodes safety guardrails, and hallucinated commands targeting non-existent devices. Sasha's study explicitly identified hallucinated device references as a key failure mode. **No guardrail system is specifically designed for smart home LLM agents**, though general-purpose tools exist (NVIDIA NeMo Guardrails, Llama Guard). Benchmark evaluation of guardrails revealed alarming generalization gaps: Qwen3Guard-8B achieved **85.3% accuracy on benchmarks but dropped to 33.8% on novel prompts**.

VESPER is critical here because it provides the only safe way to evaluate adversarial attacks against LLM-controlled physical devices. The simulated environment enables testing prompt injection, hallucinated commands, and safety violations without risk to real homes. Its known device inventory enables automated detection of hallucinated device references, and its human behavioral similarity metrics can detect when LLM agents deviate from expected patterns—a signal of adversarial manipulation.

## 3. Network intrusion detection suffers from a realism crisis

IoT network intrusion detection has produced impressive accuracy numbers on benchmarks but faces a fundamental evaluation crisis: **the gap between lab performance and real-world deployment remains largely unmeasured**.

**Kitsune** (Mirsky et al., NDSS 2018) established the architecture template with an ensemble of lightweight autoencoders processing **~5,400 packets/second on a Raspberry Pi**. Its AfterImage feature extractor computes incremental statistics per packet, enabling unsupervised anomaly detection without labeled training data. Achieving AUC comparable to offline methods across 9 attack types, it has garnered **~868 citations**. **N-BaIoT** (Meidan et al., 2018) reported **100% TPR** detecting Mirai and BASHLITE across 9 commercial IoT devices using per-device deep autoencoders with 115 statistical features—though this perfect score likely reflects the clean separation between idle benign traffic and active attacks rather than realistic detection capability.

The dataset landscape has expanded considerably. **IoT-23** (Stratosphere Lab, 2020) provides **>760 million packets** across 23 scenarios with 10 malware families, but contains only **3 benign device types** (Philips Hue, Amazon Echo, Somfy lock), all captured in idle mode without human interaction. **CICIoT2023** dramatically increased scale to **105 real IoT devices** and **33 distinct attacks** across 7 categories, with benchmark classifiers achieving >99% binary accuracy—but the lab captures brief periods without realistic multi-user dynamics. Newer datasets include **CICIoMT2024** (40 IoMT devices, 18 healthcare-specific attacks), **Gotham 2025** (78 emulated devices with MQTT/CoAP/RTSP), and **ZigBeeNet 2024** (15 Zigbee devices, 24.7 million packets over 20 days).

Recent ML approaches have pushed beyond autoencoders. **Federated learning** frameworks address privacy by training across distributed devices: Tab Transformer + FL achieved **98.80% accuracy** on CICIoT2023, while VAE-HGB under FL reached **99.14%** on N-BaIoT. **Graph neural networks** model network topology explicitly: E-GraphSAGE achieves state-of-the-art on NF-ToN-IoT, hybrid GraphSAGE+GAT reaches **98% accuracy** on UNSW-NB15, and GIDS achieves **100% F1** on some datasets. However, **REAL-IoT** (arXiv 2025) exposed a critical measurement gap: current GNN-based NIDS evaluations overestimate resilience because they use single preprocessed datasets and synthetic adversarial attacks. Their real-testbed evaluation with 4,161 NetFlow records showed **performance degradation versus public benchmarks**.

Five systemic limitations emerge across all IoT NIDS evaluation:

- **Unrealistic benign traffic**: Most datasets capture idle or minimally-used devices. A smart lock opening at 3 AM might be normal (night-shift worker) or anomalous—network-only systems cannot distinguish without behavioral context.
- **No physical/behavioral context**: Zero datasets include human activity information, room occupancy, or device interaction context alongside network captures.
- **Static snapshots**: Datasets cover brief periods; models trained on them fail to handle concept drift from evolving usage patterns, firmware updates, and new device additions.
- **Limited device diversity**: IoT-23 has 3 benign devices; even CICIoT2023's 105 devices lack Zigbee, BLE, and Thread protocol traffic. Real homes may have 30–100+ devices across 5+ protocols.
- **Lab-to-deployment gap**: Models reporting >99% accuracy show significant degradation in real environments. Hindy et al. note public datasets cover only **33% of known attacks**.

VESPER directly addresses all five limitations. LLM-driven activity generation produces temporally diverse benign traffic (morning routines, evening entertainment, guest visits). The 3D simulation provides ground-truth physical context. Continuous simulation generates evolving traffic over weeks or months. Firmware-in-the-loop scales to hundreds of emulated devices with actual protocol implementations. And deterministic simulation enables exact reproduction of evaluation scenarios.

## 4. Firmware analysis has scaled impressively but smart home coverage lags

Firmware vulnerability analysis has evolved along three parallel tracks since 2016, collectively discovering hundreds of zero-day vulnerabilities—but smart home device coverage remains limited by the peripheral emulation challenge.

**Full-system emulation** began with **Firmadyne** (NDSS 2016), which scraped **23,035 firmware images** from 42+ vendors and emulated **1,971 images** using QEMU with modified kernels, finding **846 (43%) vulnerable** to at least one of 60 Metasploit exploits plus **14 previously unknown vulnerabilities**. Its emulation success rate of **~16%** was dramatically improved by **FirmAE** (ACSAC 2020), which introduced "arbitrated emulation" with five heuristics, boosting success to **79.36% (892/1,124 images)** and discovering **12 zero-day vulnerabilities**. **Greenhouse** (USENIX Security 2023) innovated further with user-space single-service rehosting, successfully rehosting **2,841 (39.7%) of 7,140 firmware images** and finding **26 zero-day plus 717 N-day vulnerabilities**—the largest-scale firmware analysis to date.

**HAL-level replacement** targets bare-metal/RTOS firmware. **HALucinator** (USENIX Security 2020) replaces Hardware Abstraction Layer functions with generic implementations, successfully rehosting 16 firmware samples across 3 chip vendors and discovering **2 CVEs** in Contiki OS. **Pretender** (RAID 2019) uses machine learning to model peripheral behavior from hardware recordings via JTAG/SWD debug interfaces, discovering hidden backdoor functionality in rehosted firmware. The **Conware** follow-up (ASIA CCS 2021) improved on Pretender with ω-automata for portable, composable peripheral models.

**MMIO-aware fuzzing** represents the state of the art for bare-metal firmware. **Fuzzware** (USENIX Security 2022) uses symbolic execution to model MMIO accesses, reducing fuzzer input space by **up to 95.5%** and achieving up to **3.25× code coverage** across 77 firmware images on 19 hardware platforms. **Hoedur** (USENIX Security 2023) reorganized fuzzing into multi-stream typed inputs, achieving up to **5× coverage** and finding **23 previously unknown bugs** with assigned CVEs. **ES-Fuzz** (CCS 2025) added stateful MMIO models, enhancing coverage by up to **54%** on 11 of 24 firmware images.

**Companion-app fuzzing** approaches the problem from the application side. **DIANE** (IEEE S&P 2021) identifies fuzzing triggers in Android companion apps, finding **11 bugs (9 zero-days)** across 11 popular real-world IoT devices where traditional network fuzzers found **zero bugs**. **SaTC** (USENIX Security 2021) uses shared keywords between front-end and back-end to guide analysis, discovering **33 previously unknown bugs** across 39 firmware images.

Several large-scale firmware repositories support this research: the **WUSTL Firmware Dataset** contains **157,141 images (~6 TB)** from 204 vendors, Firmadyne's scraper covers 23,035+ images, Costin et al.'s corpus contains 32,000 images, and the **LFwC** (NDSS 2025) provides a Linux firmware corpus spanning 2005–2023 with vulnerability ground truth.

The central challenge remains **peripheral dependencies**—the #1 obstacle to firmware emulation. Solutions range from recording-based (Pretender), to symbolic (Fuzzware), to HAL replacement (HALucinator), to specification-guided (SEmu, which mines chip manuals via NLP). For smart home devices specifically, consumer products running Linux-based firmware (routers, cameras, hubs) benefit from Greenhouse/FirmAE, while Matter/Thread-based devices using RTOS benefit from Fuzzware/HALucinator. **FirmRec** (CCS 2024) detected **642 vulnerabilities** in 320 firmware images with **53 CVEs assigned**, demonstrating the remaining vulnerability surface.

VESPER's firmware-in-the-loop via Docker/QEMU creates several unique advantages: ground-truth validation of emulation fidelity by running identical firmware on real ARM hardware and in emulated tools; automated MMIO trace collection for Pretender-style peripheral model training without physical hardware; scalable companion-app fuzzing by replacing DIANE's physical device requirement; and a standardized firmware benchmark where all tools evaluate against the same corpus.

## 5. Cross-app attacks span platforms, protocols, and physical channels

Cross-app interaction research has documented an extensive attack surface across SmartThings, IFTTT, and now Matter, revealing that the composition of individually secure apps creates dangerous emergent behaviors.

The foundational work by **Fernandes et al.** (IEEE S&P 2016) analyzed **499 SmartThings apps**, finding **over 55% were over-privileged** and constructing 4 proof-of-concept attacks including secretly planting door lock codes. **SmartAuth** (Tian et al., USENIX Security 2017) addressed this with NLP-based authorization analysis of **180 SmartApps**, finding **16.7% exhibit undisclosed overprivilege**, and reducing user installation of overprivileged apps from **48% to 16%** in a 100-participant study. **SaINT** (USENIX Security 2018) performed static taint analysis on **230 SmartThings apps**, finding **60% include sensitive data flows**, and introduced **IoTBench**—an open-source test suite with 19 malicious apps containing 27 unique data leaks.

Physical-channel interactions represent a particularly dangerous and under-studied attack vector. **IoTMon** (CCS 2018) discovered **162 hidden inter-app interaction chains** through physical channels (humidity, temperature, motion, illumination) across 185 SmartThings apps, with **37 identified as highly risky**. Its follow-up **IoTSAFE** (NDSS 2021) validated these in a 3-room smart home, achieving **~96% accuracy** in predicting risky temporal physical interactions and preventing **53 highly risky conditions**. **ProvThings** (NDSS 2018) provided forensic capability through provenance-based auditing, instrumenting SmartThings apps with only **5% overhead** and **260 KB daily storage** to construct causal graphs across 26 known IoT attacks.

The **IoT Phantom-Delay Attack** (DSN 2022, the NSF paper) revealed a protocol-level vulnerability: timeout detection in TCP is decoupled from data protection in TLS, enabling event and command message delays that cause spurious, disabled, or erroneous automation execution. Testing **50 popular IoT devices**—all were vulnerable. Google, Ring, and SimpliSafe acknowledged the issues.

Matter protocol security is emerging as a critical new frontier. **Wang et al.** (SDIoTSec/NDSS 2024) identified covert control channels in Apple Home's Matter implementation where attackers can masquerade as Apple Keychain services (VendorID 4996), remaining invisible in Apple Home's interface. The root cause—absence of authentication for VendorID—was **acknowledged by the Connectivity Standards Alliance**. A comprehensive 2025 IACR analysis found cryptographic weaknesses in Matter's PASE and CASE key establishment protocols, recommending replacement of **PBKDF2 with memory-hard alternatives (Argon2)**. Matter's inconsistent ecosystem implementation compounds the problem: SmartThings progresses rapidly while Google Home remains stuck at v1.2.

VESPER needs to support multi-platform app corpora (SmartThings, IFTTT, Home Assistant YAML, Matter device configs), combined static+dynamic analysis workflows, physical interaction simulation for IoTMon-style chain validation, network-level attack simulation for Phantom-Delay-style timing attacks, and Matter commissioning/fabric management testing.

## 6. The evaluation infrastructure gap is the field's biggest bottleneck

Cross-cutting analysis reveals that **fragmented evaluation is the single largest obstacle to progress in smart home security research**. This conclusion is supported by multiple independent lines of evidence.

**Attack taxonomies are fragmented.** Heartfield et al. (2018) classify **25 distinct smart home attacks** along attack vector and impact dimensions. Hammi et al. (2022) propose a separate taxonomy for security requirements and cyberattacks. ACM Computing Surveys (2024) adds a taxonomy of decision-making approaches. PRASH (2021) focuses on privacy attacks. Applied Sciences (2025) introduces a four-axis taxonomy (system level, algorithmic paradigm, data granularity, hardware budget). No single taxonomy covers the full cyber-physical attack surface including physical-world consequences.

**No standardized benchmark exists.** The closest attempts include **SCI-IoT** (2025), which proposes 30 trust tests for individual device certification but not system-level security; **OWASP IoT Top 10** (2018), which lists threat categories without evaluation methodology; and **VetIoT** (2023), which automates testing of runtime policy enforcement tools but uses virtual devices without physical simulation. Physical testbeds like Alzhrani et al. (2019) and the PMC/Sensors 2025 testbed provide attack detection capabilities but are not reproducible or scalable.

**Digital twins for IoT security are nascent.** An ACM Computing Surveys analysis (2025) of **201 publications** on digital twins for security operations found the field is in early stages, with only 5 prior surveys investigating DTs for cybersecurity. El-Hajj (2024) integrated Eclipse Ditto with Snort IDS on Raspberry Pi but struggled with reconnaissance scan detection. Most DT security work targets industrial/critical infrastructure, **not consumer smart homes**. No existing DT platform combines photorealistic 3D rendering with IoT protocol simulation and security testing.

**Recent surveys unanimously call for unified platforms.** The ACM Computing Surveys (2024) review of knowledge-based cyber-physical security explicitly calls for standardized evaluation methods and comprehensive testbeds. The 2025 Alosaimi et al. systematic review of testbeds for anomaly detection in built environments represents the closest work to articulating the need for unified evaluation frameworks. MDPI Electronics (2024) identifies "unified architecture" as a key future direction. **NIST SP 1343** (2025) addresses smart home security from a standards perspective, reinforcing the need for standardized testing.

**Habitat 3.0** (Meta AI, ICLR 2024) provides the 3D simulation foundation VESPER needs: accurate humanoid simulation, human-in-the-loop infrastructure, collaborative task support, and rendering of **211 high-quality 3D scenes** with 18,656 object models at **>8,000 simulation steps/second**. No one has applied embodied AI simulation to IoT security—VESPER would be first.

## 7. What VESPER must provide: a unified capability matrix

Synthesizing the evaluation gaps across all 50+ surveyed systems, VESPER needs the following capabilities to serve as a universal evaluation platform:

**Physical environment simulation layer.** This is the single most requested missing capability. HAWatcher needs it for sensor correlation validation. HomeGuard explicitly cannot detect physical-channel violations without it. IoTMon's 162 interaction chains need physical grounding. N-BaIoT's 100% TPR needs stress-testing against realistic benign traffic. VESPER must model temperature, humidity, light, sound, motion, and air quality with sufficient fidelity that physical-channel attacks (e.g., a heater triggering a temperature sensor that opens a window) produce correct cascading effects.

**Firmware-in-the-loop execution.** Docker/QEMU running real ARM firmware addresses Firmadyne's 16% emulation success rate, replaces DIANE's physical device requirement, enables Pretender-style peripheral model training, and provides the actual protocol implementations that network IDS tools need for realistic traffic generation. VESPER should support both Linux-based firmware (via FirmAE/Greenhouse-style approaches) and bare-metal/RTOS firmware (via Fuzzware/HALucinator-style MMIO modeling).

**LLM-driven activity generation.** This addresses the most universal limitation: lack of realistic human behavior in evaluation. Every NIDS dataset suffers from monotonous benign traffic. Rule safety tools use hand-crafted scenarios. LLM security tools have no standardized adversarial benchmarks. VESPER's activity generation must produce temporally diverse daily routines (morning, daytime, evening, night), multi-occupant behaviors, seasonal variations, and anomalous-but-benign events (guests, schedule changes, new devices) to serve as realistic baselines across all tool categories.

**Multi-platform automation engine.** Supporting SmartThings, Home Assistant, IFTTT-style trigger-action rules, and Matter device configurations in a common framework. This enables cross-platform evaluation of tools currently locked to single ecosystems. A common intermediate representation for automation rules (as proposed by Celik et al.) would allow tools like Soteria, iRuler, and SIGFRID to evaluate against identical rule sets across platforms.

**Network capture and attack injection.** Full packet capture at the virtual network layer, with the ability to inject attacks (DDoS, botnet C&C, scanning, data exfiltration, message delay) during simulated daily activities. This generates contextually rich datasets that address every limitation of IoT-23, CICIoT2023, and N-BaIoT. Attack injection must be temporally synchronized with physical simulation state for meaningful evaluation.

**Standardized benchmark suite.** A curated set of scenarios with known ground truth covering all five research categories: rule safety violations (extending IoTBench's 19 apps), LLM adversarial commands (extending HomeBench), network attacks during realistic usage, firmware vulnerabilities in emulated devices, and cross-app interaction chains. Each scenario must include expected outcomes, enabling automated comparison of tool performance.

**Metrics and evaluation API.** Standardized metrics spanning detection rate, false positive rate, response time, resource overhead, and—uniquely—**physical safety impact** (did the violation result in a dangerous physical state?). Tools should plug in via a defined API that receives environment state, network traffic, automation events, and device telemetry, and reports detected violations or executed defenses.

## Conclusion: five research streams, one platform gap

This survey of 50+ systems across smart home rule safety, LLM-based control, network intrusion detection, firmware analysis, and cross-app interaction attacks reveals a research field producing increasingly sophisticated individual tools that cannot be meaningfully compared because no common evaluation infrastructure exists. The pattern is consistent across all categories: tools evaluate on proprietary testbeds with incomparable metrics, then acknowledge in their limitations sections the lack of realistic physical environments, diverse device populations, and human behavioral context.

Three findings stand out as particularly actionable for VESPER's design. First, **physical-channel modeling is the highest-value capability**—it is the most cited limitation (HomeGuard, IoTMon, all NIDS datasets) and the one no existing platform provides. Second, **LLM smart home security is an urgent gap**: four major systems control physical devices without any formal security evaluation, creating a ready-made first use case for VESPER. Third, **the firmware-in-the-loop approach has strong precedent**: the firmware analysis community has built extensive infrastructure (157,000+ firmware images, mature emulation tools, established vulnerability corpora) that VESPER can directly leverage rather than building from scratch.

The most immediate and impactful contribution VESPER can make is generating **contextually grounded evaluation datasets**—combining 3D physical state, network traffic, automation events, and human activity traces in a single synchronized capture. No such dataset exists today, and every surveyed system would benefit from one. By providing this capability alongside a plug-in evaluation API and standardized benchmark scenarios, VESPER transforms from a research prototype into the connective tissue the smart home security field has been missing.
